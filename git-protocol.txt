GIT PROTOCOL - fpga-audio-source-classifier


You all know Git, so this isn't a tutorial. These are the conventions we
will use so there isn't conflict.


Branches
- main only changes through PRs. No direct pushes, no force-pushes.

- Name branches <area, etc.>, lowercase with dashes like:
    training/mfcc-features

- One task per branch. Keep it open as long as you need, but merge main
  into it at the start of every session so it doesn't drift.

- Once a branch is pushed, use merge, not rebase.


Commits
- Commit each finished step and push it. Pushed commits are our progress
  record and your backup.

- Write specific messages like: "Add MFCC features for 1 s
  windows", not "stuff" or "fixes".

- Stage files explicitly and check git status first. No blind "git add ."

- Don't reformat, rename, or move files outside your task.

- Leave .gitattributes alone; it handles Windows/Linux line endings.


PR
- Merge main into your branch and re-test before opening the PR.

- Say what changed and how you tested it.

- The area I review. If there's no response in 3 days, you may merge
  it yourself.

- Merge with "Create a merge commit", not squash, so the history keeps
  every commit. Delete the branch afterward.


Folder Ownership
I'll review PRs in their area. If you need to change someone else's
area, flag it in the chat or the PR.


Results and Notebook - Only for the ppl training the model
- Every training run gets results/<YYYY-MM-DD>-<your-name>-<short-name>/
  (what you tried, why, and what happened), and the model if it's small
  (.onnx or .tflite, under 5 MB).

- Notebooks keep their outputs so results read on GitHub. One per person:
  training/notebooks/<your-name>-<topic>.ipynb. Never edit someone
  else's notebook; copy it.

- Design decisions and progress updates go in docs/.


Hardware and Firmware
- Vivado: Never commit the project itself; build it into hardware/build/. 

- .xsa: only Adam updates it (in hardware/) and announces it, since 
  firmware has to regenerate its platform.

- Vitis: keep the workspace outside the repo or in firmware/build/.
  Commit only firmware/src, etc.

- firmware/model/ is generated by the training export script. Never
  hand-edit or hand-merge it; on a conflict, take main's version and
  re-export.


Keep out of git
- Datasets and recordings. They live in data/ (ignored).

- Checkpoints (.pt, .pth, .ckpt). Share them through the team folder if
  someone needs one.

- Build output, .venv, archives, and any file over 5 MB.

- Passwords and API keys. The repo is public, and bots scan for them.

- If .gitignore misses something, fix it in a separate PR.

- Don't use git, to upload the dataset because of its file size limits
  One channel: about 2.8 GB per hour of recording.
  All 64 TDM channels: about 177 GB per hour.
  Up to ~100 GB: University OneDrive or Google Drive
  Over ~100 GB: USB SSD in person.


Data Handoff - Only for the ppl sending me data
- Only send the channels that actually carry sources, not the full
  64-channel capture.

- Keep the original WAVs. Don't convert to MP3 or downsample; I'll do
  that in preprocessing.

- Put each batch in its own dated folder, like recordings-2026-10-05/.
  New recordings go in a new batch; never overwrite one I already have.

- Every batch includes:
    README.txt   sample rate, bit depth, which channel = which source,
                 mic setup, date, anything unusual
    labels.csv   file, start_s, end_s, labels (like "piano;vocal")
    audio/       the original WAVs
    SHA256SUMS   checksums so I can verify the download

- Use the class names from the list I share. Ask me before adding a new
  one.

- Make the checksums in Git Bash or Linux: sha256sum audio/* > SHA256SUMS

- Tell me when a batch is fully uploaded so I don't start training on a
  half-finished folder.


Conflict
- If a conflict is in someone else's code, ask them before resolving it.

- Regenerate generated files (firmware/model/) instead of merging them.
