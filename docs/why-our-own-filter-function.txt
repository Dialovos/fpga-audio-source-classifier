We'll have to create our own filter function using SciPy since some of the ones I looked at on the web to copy from didn't match what we might want in this project. We can use the SciPy, which will do what we want: pipeline/filters.py designs every filter with scipy.signal.iirfilter, applies it with scipy.signal.sosfilt, and checks it with scipy.signal.sosfreqz.

We can keep a small adapter on top of SciPy with it exists because our filter step has a stricter job than most audio code. Every ex we generate becomes training or test data, so its label has to match the filter that was really applied. Every label follows one order rule where order is the total number of poles because SciPy's band-pass with order N ends up with order 2N. It also means supporting the families we might test, which are Butterworth, Chebyshev I & II, and elliptic. The filter runs in one pass from a zero starting state, so the label matches the response. Every ex saves a JSON record of its settings + coefficients, and the coefficients stay in second-order sections so the C/FPGA version can check against the same reference. Bad or typo  settings get rejected instead of quietly changed. If everyone called SciPy directly in their own scripts, those rules would drift from person to person. The wrong label is hard to notice once it's in the dataset.

I searched for a library that already does this, and none of them gives us labels we directly. audiomentations (v0.43.1) has high-pass, low-pass, and band-pass filters with random settings, but they're Butterworth only. If a cutoff lands past Nyquist, it quietly clamps the cutoff but keeps the old value in its saved parameters, so the label can be wrong. By default it only applies the filter 50% of the time. It sets band-pass by center frequency and bandwidth, with steepness in dB/octave, and it starts each filter from a guessed state instead of zero. pyfar is the closest fit, since it has all four families and gives us second-order sections. It wraps SciPy, though, so its band-pass order follows SciPy's rule, and its FilterSOS.order always reports twice the number of sections, so a 3rd-order filter shows up as 4. torchaudio's biquad filters are fixed at 2nd order. pedalboard only has simple fixed-slope filters, plus a ladder filter with 12 or 24 dB modes. pysox needs the SoX program installed, and its normal effects don't hand back the coefficients we'd need for labels. Every one of these would still need our own label step on top, so we keep the adapter small and treat it as the one shared place for the order rule and the records. The case against it is that one shared generator script could call SciPy directly and do the same job with less code. I think we should keep the module because everyone shares it and it cuts labeling mistakes. To keep it reliable, it'll reject settings that don't apply to a family, along with anything that isn't a real number in range. We'll rebuild examples from the saved coefficients instead of redesigning the filter, save the library versions in each record, and use those saved coefficients as the reference when we check the C/FPGA version.
