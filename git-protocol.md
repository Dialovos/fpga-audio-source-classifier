# Git Protocol - fpga-audio-source-classifier

You all know Git, so this isn't a tutorial. These are the conventions we will use so there isn't conflict.

## Branches

- `main` only changes through PRs. No direct pushes, no force-pushes.

- Name branches `<area>/<topic>`, lowercase with dashes, like `pipeline/filter-id` or `data/signal-generator`.

- One task per branch. Keep it open as long as you need, but merge `main` into it at the start of every session so it doesn't drift.

- Once a branch is pushed, use merge, not rebase.

## Commits

- Commit each finished step and push it. Pushed commits are our progress record and your backup.

- Write specific messages like "Add band-pass filters to the signal generator", not "stuff" or "fixes".

- Stage files explicitly and check `git status` first. No blind `git add .`

- Don't reformat, rename, or move files outside your task.

- Leave `.gitattributes` alone; it handles Windows/Linux line endings.

## PR

- Merge `main` into your branch and re-test before opening the PR.

- Say what changed and how you tested it.

- I review the PRs. If there's no response in 3 days, you may merge it yourself.

- Merge with "Create a merge commit", not squash, so the history keeps every commit. Delete the branch afterward.

## Folder Ownership

I'll review the PRs. If you need to change something in someone else's area, flag it in the chat or the PR.

## Results and Notebook - Only for the ppl training the models

- Every run gets its own folder, `results/<YYYY-MM-DD>-<your-name>-<short-name>/`, with the metrics, plots, a `notes.txt` (what you tried, why, and what happened), the generator settings and seed it used, and the model if it's small (`.onnx` or `.tflite`, under 5 MB).

- Notebooks keep their outputs so results read on GitHub. One per person: `pipeline/notebooks/<your-name>-<topic>.ipynb`. Never edit someone else's notebook; copy it.

- Design decisions and progress updates go in `docs/`.

## Hardware and Firmware

- Vivado: never commit the project itself; build it into `hardware/build/`.

- `.xsa`: only Adam updates it (in `hardware/`) and announces it, since firmware has to regenerate its platform.

- Vitis: keep the workspace outside the repo or in `firmware/build/`. Commit only `firmware/src`, etc.

- `firmware/model/` is generated by the training export script. Never hand-edit or hand-merge it; on a conflict, take main's version and re-export.

## Keep out of Git

- Datasets, recordings, and generated test signals. They live in `data/` (ignored).

- Checkpoints (`.pt`, `.pth`, `.ckpt`). Share them through the team folder if someone needs one.

- Build output, `.venv`, archives, and any file over 5 MB.

- Passwords and API keys. The repo is public, and bots scan for them.

- If `.gitignore` misses something, fix it in a separate PR.

## Data and Test Signals

- Public datasets: download them yourself into `data/`. Don't commit or re-share copies; everyone pulls from the source so we all have the same version.

- Generated test signals don't get shared at all. Commit the generator script and its settings, and anyone can rebuild the exact same set from the same seed.

- Every generated set gets a `labels.csv` with the filter type, order, cutoffs, plus the events in each file, so the labels come with the audio.

- Use the event class names (like "rumble;thump"). Ask before adding a new one.

- If you record audio for us, put each batch in its own dated folder like `recordings-2026-10-05/` and share it through University OneDrive or Google Drive, not Git:

  ```
  README.txt   sample rate, bit depth, mic setup, date, anything unusual
  labels.csv   file, start_s, end_s, labels (like "rumble;thump")
  audio/       the original WAVs (no MP3, no downsampling)
  SHA256SUMS   checksums, made in Git Bash/Linux: sha256sum audio/* > SHA256SUMS
  ```

- Tell me when a batch is fully uploaded so I don't start on a half-finished folder.

## Conflict

- If a conflict is in someone else's code, ask them before resolving it.

- Regenerate generated files (`firmware/model/`) instead of merging them.
